# 项目增量工作流

本文件规定一次讨论如何转化为可追溯、可持续更新的仓库变更。

## 1. 输入分类

收到用户新内容后，先逐条标记：

- **确认**：用户明确同意，进入当前基线；
- **新增**：此前没有的新系统或细节；
- **修改**：对现有结论的局部调整；
- **异议**：用户不同意现有方案；
- **弃用**：旧方案被明确替代；
- **建议**：AI提出但用户尚未确认；
- **待讨论**：信息不足或需要原型验证。

同一段内容可能同时包含多种状态，必须拆开处理。

## 2. 修改范围判定

### PATCH

措辞、参数、局部规则和小型细节调整，只修改相关段落。

### MINOR

新增完整系统、重要设计支柱、核心交互或新的项目治理能力。需要新增专题文档，并把摘要同步进主设计稿。

### MAJOR

只有游戏核心类型、主要世界结构或整体产品目标发生根本变化时使用。不得因普通讨论擅自提升为MAJOR。

## 3. 每轮必做文件

| 内容 | 必须更新的位置 |
|---|---|
| 完整一问一答 | `docs/conversations/YYYY-MM-DD-round-NNN.md` |
| 本轮结论与执行 | `docs/session-logs/` |
| 当前有效总规则 | `docs/design/00-master-game-concept.md` |
| 详细系统设计 | 对应 `docs/design/` 专题文件 |
| 重大取舍 | `docs/decisions/README.md` 或独立ADR |
| 版本变化 | `CHANGELOG.md` |
| 当前版本 | `README.md`、主设计、`VERSIONING.md`、HTML构建器 |
| AI工作规则 | `AGENTS.md` 与 `docs/project-rules/` |
| 新素材 | `assets/` 与资产清单 |
| 总览 | `PvZ-Infinite-Archive.html` 与 `index.html` |

## 4. 主设计稿修改方法

1. 找到现有对应章节。
2. 保留无冲突内容。
3. 只添加或替换本轮涉及的段落。
4. 原方案被否定时，在原位置追加弃用说明。
5. 详细参数放进专题文档，主设计只保留能维持整体一致性的摘要。
6. 更新当前待决问题，删除已经确认的问题，但不要删除其历史记录。

## 5. 弃用想法模板

```md
> **弃用想法：原方案。**
> 弃用原因：……
> 当前方案：……
```

名称替换使用：

```md
> **弃用名称：旧名称。**
> 原因：……
> 当前名称：……
```

旧方案仍保留在原始问答和变更日志中。

## 6. 对话归档规则

- 一次用户发言和紧随其后的完整AI回复为一轮。
- 保留用户原文、AI正式回复和关键执行状态。
- 图片、音频等动态产物用资产路径和元数据引用，不用文字假装二进制已经保存。
- 新轮次加入 `docs/conversations/README.md`。
- 未完成的当前轮不得伪造最终执行结果；完成后补齐。

## 7. 游戏系统设计检查

任何新系统至少回答：

1. 玩家为什么会觉得有趣？
2. 它属于永久层、农场资产层、角色层还是夜间构筑层？
3. 自动与手动控制如何切换？
4. 单人、合作和PvP中的规则是否一致？
5. 如何防止无限滚雪球、复制漏洞和付费战力？
6. 死亡、摧毁、衰败和恢复的代价是什么？
7. 对AI、寻路、网络同步、性能和画面可读性的要求是什么？
8. 首个原型验证什么，哪些延后？

## 8. 素材工作流

每个素材记录：

- 原始路径和规范路径；
- 文件类型、尺寸和字节数；
- SHA-256；
- 作者、来源和许可；
- 生成提示或制作说明；
- 使用场景；
- 当前状态：概念、临时、可商用、待替换或弃用。

GLTF项目必须把 `.gltf`、`.bin`、纹理和许可文件放在同一可解析目录结构中；优先交付单文件 `.glb`。

## 9. HTML与Pages工作流

1. 保持Pages发布源为 `main / (root)`，除非后续架构明确迁移。
2. 根目录必须存在 `index.html`。
3. 运行 `python tools/build_archive.py`。
4. 检查HTML中的文件数量、总字节数和快照SHA-256。
5. 检查Markdown、图片、音频、视频、PDF、GLB和GLTF预览。
6. 检查规则文件可从侧栏找到。
7. 检查单文件导出后SHA-256与源文件一致。
8. 自动构建失败时不得声称Pages已经更新。

## 10. 提交与验证

推荐提交顺序：

1. 规则和专题设计；
2. 增量迁移脚本；
3. HTML构建器与Pages入口；
4. 对话和纪要；
5. 启动自动构建；
6. 核对自动提交后的HEAD。

最终报告必须包含：

- 分支和最终HEAD；
- 当前概念版本；
- 新增、修改和弃用内容；
- HTML快照文件数与哈希；
- Pages配置是否需要用户操作；
- 未完成或未验证事项。

## 11. Definition of Done

- [ ] 用户本轮所有明确要求均有对应产物；
- [ ] 没有删除旧细节；
- [ ] 弃用方案已回写原章节；
- [ ] 主设计和专题设计一致；
- [ ] 对话、纪要、变更日志和决策已同步；
- [ ] AI接手规则仍准确；
- [ ] HTML重建成功；
- [ ] Pages根入口存在；
- [ ] 多格式预览至少通过静态检查；
- [ ] 所有失败均如实报告。
